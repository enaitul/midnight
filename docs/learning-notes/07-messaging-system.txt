2. REST APIS VERSUS WEBSOCKETS
------------------------------
| Attribute | Traditional REST (HTTP) | WebSockets (Flask-SocketIO) |
|---|---|---|
| Protocol | HTTP/1.1 or HTTP/2 | `ws://` or `wss://` (TCP persistent) |
| Connection | Short-lived: Request -> Response -> Close | Persistent, bi-directional full-duplex socket |
| Latency | Higher: TCP handshake + HTTP headers on every message | Minimal: Frames are sent immediately across open pipe |
| Server Push | Cannot push (client must poll server repeatedly) | Server can push events to client at any millisecond |
| Best For | Crud operations, search, uploads, initial sync | Live chat, typing indicators, instant notifications |

OUR HYBRID ARCHITECTURE:
- WebSockets handle real-time message broadcasting and room events.
- REST handles initial message history loading, pagination, group creation,
  and offline fallback if WebSockets are temporarily unavailable.

3. FLASK-SOCKETIO ARCHITECTURE & AUTHENTICATION
-----------------------------------------------
SOCKET INITIALIZATION (`server/app/__init__.py`):
```python
socketio = SocketIO(cors_allowed_origins='*')
```

HANDSHAKE AUTHENTICATION (`server/app/socket_events.py`):
When the React client connects:
```javascript
const socket = io(url, { auth: { token } })
```
On the Flask backend:
```python
@socketio.on('connect')
def authenticate_socket(auth):
    token = auth.get('token') if isinstance(auth, dict) else None
    if not token:
        return False # Immediately terminates connection
    user_id, error = decode_jwt_token(token)
    if error or not db.session.get(User, user_id):
        return False
    session['midnight_user_id'] = user_id
    join_room(f'user:{user_id}') # Personal user room for notifications
```
If the token is invalid or expired, the connection is instantly rejected at the TCP level.

ROOM AUTHORIZATION (`join_conversation`):
```python
@socketio.on('join_conversation')
def join_conversation(data):
    user_id = session.get('midnight_user_id')
    conversation_id = data.get('conversation_id')
    # CRITICAL: Verify user is an active participant in PostgreSQL!
    if not membership(conversation_id, user_id):
        return {'ok': False, 'error': 'Conversation not found'}
    join_room(f'conversation:{conversation_id}')
    return {'ok': True}
```
Non-members can NEVER join or listen to unauthorized conversation rooms.

4. DATABASE RELATIONSHIPS & SCHEMA DESIGN
-----------------------------------------
Three relational models manage the messaging ecosystem:

1. `Conversation` (`conversations` table):
   - `id`: Integer Primary Key
   - `kind`: `'direct'` or `'group'`
   - `name`: Group name (nullable for direct)
   - `direct_key`: Sorted composite key (e.g. `'4:12'`), `UNIQUE`. Prevents duplicate
     direct conversations at the database level!
   - `created_by_id`: User ForeignKey (nullable, `ON DELETE SET NULL`)
   - `created_at` & `updated_at`: UTC timestamps

2. `ConversationParticipant` (`conversation_participants` table):
   - `conversation_id`: ForeignKey to `conversations.id` (Composite PK, `ON DELETE CASCADE`)
   - `user_id`: ForeignKey to `users.id` (Composite PK, `ON DELETE CASCADE`)
   - `role`: `'admin'` or `'member'`
   - `joined_at` & `last_read_at`: UTC timestamps

3. `Message` (`messages` table):
   - `id`: Integer Primary Key
   - `conversation_id`: ForeignKey to `conversations.id` (Indexed, `ON DELETE CASCADE`)
   - `sender_id`: ForeignKey to `users.id` (Indexed, `ON DELETE CASCADE`)
   - `body`: String(5000), NOT NULL
   - `created_at` & `updated_at`: UTC timestamps
   - Index: Composite B-Tree index on `(conversation_id, created_at)` for instant
     chronological history queries.

5. REAL-TIME MESSAGE LIFECYCLE
------------------------------
1. Sender types message in React `<form className="message-composer">` and presses Enter.
2. React emits `send_message` event: `{ conversation_id: 12, body: "Hello" }`.
3. Flask Socket event handler receives payload:
   - Validates authenticated `session['midnight_user_id']`.
   - Validates message body length (1 to 5,000 characters).
   - Verifies sender's membership in `conversation_id`.
4. Message is inserted into PostgreSQL `messages` table and committed (`db.session.commit()`).
5. Flask broadcasts `new_message` event to room `f'conversation:{conversation_id}'`.
6. All connected members currently inside the room receive the event in real time.
7. Any member currently offline will receive the message upon their next REST sync
   (`GET /api/conversations/<id>/messages`).

6. ONE-TO-ONE VS GROUP PERMISSIONS
----------------------------------
DIRECT CONVERSATIONS:
- Can only involve exactly 2 users.
- Cannot start a direct conversation with yourself (`user_id == other_id` returns 400).
- Idempotent: Attempting to start an existing conversation returns the existing conversation
  object with HTTP 200 rather than creating duplicates.

GROUP CONVERSATIONS:
- Creators are automatically designated with `role = 'admin'`.
- Only `admin` participants can:
  - Add new members (`POST /api/conversations/<id>/participants`).
  - Remove members (`DELETE /api/conversations/<id>/participants/<user_id>`).
  - Rename the group (`PUT /api/conversations/<id>/name`).
- Ordinary members can read, send messages, and leave the group (`POST /api/conversations/<id>/leave`).
- Admin Succession: If the only admin leaves, admin privileges automatically transfer
  to the next oldest member.
- Auto-Cleanup: If the last member leaves, the group conversation and messages are deleted.

9. SDE INTERVIEW PREPARATION (12 QUESTIONS & ANSWERS)
-----------------------------------------------------
Q1: How do WebSockets handle authentication compared to standard REST requests?
A: In standard REST, every single HTTP request transmits an `Authorization: Bearer <token>` header.
In WebSockets, authentication typically occurs during the initial HTTP Upgrade handshake via an
`auth` dictionary or query parameter. Once the handshake succeeds, the TCP socket connection remains
open and authenticated for its entire duration.

Q2: Why should you never trust a client-supplied conversation ID when joining a socket room?
A: An attacker could connect with their own valid account, and then emit `join_conversation` with an
arbitrary ID (e.g. `conversation_id: 42`). If the server blindly calls `join_room(f'conversation:42')`,
the attacker would eavesdrop on private messages. The server must verify that the authenticated
`user_id` is an active member in the database before calling `join_room`.

Q3: How do you prevent duplicate 1-on-1 direct conversations between two users in the database?
A: Generate a deterministic composite key by sorting the two user IDs:
`':'.join(map(str, sorted((user_a_id, user_b_id))))` (e.g. `'4:12'`).
By adding a `UNIQUE` constraint on the `direct_key` column in PostgreSQL, any concurrent attempt
to create a duplicate conversation is safely rejected by the database engine.

Q4: What is the purpose of composite primary keys on join tables like `conversation_participants`?
A: Setting `(conversation_id, user_id)` as a composite primary key automatically enforces that a
user can only be added to a conversation once, prevents duplicate memberships without needing a
surrogate integer `id`, and automatically indexes lookups on `conversation_id`.

Q5: Why is message persistence executed BEFORE emitting the socket event?
A: If the server emits the socket event before committing to PostgreSQL and the database crashes
or rejects the insert (due to constraint violation or power failure), the recipient sees a message
on their screen that does not exist in history. When they refresh the page, the message vanishes.
Persisting first guarantees durability (ACID).

Q6: How do you handle clients reconnecting after an intermittent network drop?
A: When a client reconnects, it re-establishes the socket connection and calls the REST endpoint
`GET /api/conversations/<id>/messages?before=<id>` to fetch any messages that occurred during the
disconnection window, seamlessly merging them into local state.

Q7: What is the purpose of the composite index on `(conversation_id, created_at)` in messages?
A: Queries fetching chat history always filter by `conversation_id` and sort by `created_at`.
A composite B-Tree index allows PostgreSQL to jump directly to the target conversation's rows and
stream them in pre-sorted order, avoiding full table scans or in-memory quicksorts.

Q8: What is the trade-off of using WebSockets vs Server-Sent Events (SSE) for chat?
A: Server-Sent Events are unidirectional (server to client only) over HTTP. They are easier to
set up for notifications, but sending messages requires separate HTTP POST requests. WebSockets
are bi-directional, lower latency, and support duplex messaging over a single connection.

Q9: What happens when the only admin of a group chat leaves?
A: An admin succession algorithm must run: the server selects the next oldest member (by `joined_at`)
and promotes them to `admin` before deleting the leaving user. If no other members remain, the
entire conversation and its messages are removed.

Q10: Why should messages enforce a maximum length (e.g. 5,000 characters)?
A: To prevent Denial of Service and database bloat. Malicious users could send multi-megabyte text
strings that exhaust socket buffers, flood database write queues, and cause client-side browser DOM
freezes.

Q11: How do read receipts / unread badges work without updating every single message row?
A: Instead of storing `is_read` on every message row (which requires updating hundreds of rows),
store a single `last_read_at` timestamp on `conversation_participants`. The unread count is simply:
`SELECT COUNT(id) FROM messages WHERE conversation_id = ? AND sender_id != ? AND created_at > participant.last_read_at`.

Q12: How does WebSocket scaling work across multiple server nodes in production?
A: In a multi-node cluster, User A might be connected to Server 1 while User B is connected to
Server 2. Emitting to a room on Server 1 would not reach User B. To fix this, production setups
use a Redis message broker with the Socket.IO Redis adapter (Pub/Sub) to synchronize events
across all cluster nodes.
