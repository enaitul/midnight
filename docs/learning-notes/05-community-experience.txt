midnight. — Community Experience
================================

1. Milestone objective
----------------------
This milestone turns the community navigation, profile, search, saved-writing,
and messaging screens into connected features. The work keeps the existing
React/Vite, Flask, SQLAlchemy, PostgreSQL, JWT, and Flask-Migrate architecture.
New database tables and columns are additive; existing users and posts are kept.

2. Features implemented
-----------------------
- Reordered the sidebar to Feed, New post, Messages, Search, and About. On
  mobile it uses icons only, with the account picture and name in the top bar.
- Set the midnight. wordmark in a quiet serif face. The feed now opens with the
  signed-in greeting and Begin a new page? followed by Recent writings.
- Added public profiles and a private owner edit view for display name, bio,
  optional age, and age visibility. PNG, JPEG, and WebP profile-picture uploads
  are size limited and checked against their file signatures.
- Added published-writing contribution counts, calculated from database rows.
- Added private saved-writing records and controls on the feed and detail view.
- Added database search for published writing and public user fields. The UI
  debounces requests and has loading, error, and empty states.
- Added persistent one-to-one and group conversations, message history, unread
  counts, group administrators, membership changes, and leaving groups.
- Added authenticated Socket.IO connect, join, and send events. REST and socket
  sends both save to the database before messages are delivered.
- Combined the product and creator details in About, including the supplied
  creator photo, name, motivation, LinkedIn, and portfolio links.
- Added post likes, comments, Author labels on the author's own comments, and
  image/audio/video attachments with previews. Enter submits comments and sends
  chat messages; Shift+Enter inserts a line break.
- Posts may omit a title, and photo/video posts can be published without body
  text. Attached media is stored with a 25 MB combined request limit.
- Kept the complete feed writing, theme toggle, drafts, publishing, and editing.

3. Architecture and data flow
-----------------------------
React pages use `communityService`, which calls the Flask JSON API through the
existing Axios instance. The request interceptor attaches the existing JWT.
Flask route handlers validate input and authentication, call SQLAlchemy models
and services, then return JSON. PostgreSQL persists profiles, saved-writing
records, conversations, participants, and messages.

For live chat, Socket.IO authenticates the same JWT during the connection. A
client must ask to join a conversation room; the server checks that the user is
a participant. A socket send checks membership again, validates the text, saves
the message, and only then emits it to that conversation room. REST message
history uses the same database. A reconnect or another login can reload history.

The Vite development server proxies `/api` to Flask on port 5000. In development,
the Socket.IO client connects directly to `http://127.0.0.1:5000` so the browser
can establish a WebSocket. Set `VITE_SOCKET_URL` to choose another server. In
production, it defaults to the frontend origin, so a reverse proxy must forward
`/socket.io` with WebSocket upgrade support. Set
`SOCKETIO_CORS_ALLOWED_ORIGINS` to the permitted browser origins. Production
hosting must use a shared, persistent avatar directory if it runs more than
one server instance.

4. Database models and relationships
------------------------------------
`User` gains `display_name`, `biography`, `age`, and `age_public`. A user has
many posts, saved writings, and conversation memberships. Public serializers
never return email. Age is included in public profile data only when
`age_public` is true; the signed-in owner can see their own age and email.

`SavedWriting` links one user to one post. A unique constraint prevents saving
the same post twice. Foreign keys cascade when a user or post is removed. The
API only allows published posts to be saved and always scopes reads to the
signed-in user.

`Conversation` is either `direct` or `group`. A unique sorted `direct_key`
prevents duplicate one-to-one conversations. `ConversationParticipant` links a
user to a conversation and records the `admin`/`member` role, join time, and
last-read time. `Message` belongs to a conversation and sender, and stores up
to 5,000 characters with a timestamp. Foreign keys and indexes support member
lookups and chronological history.

Migration `8d4c2b91f6a0` follows the existing Milestone 4 head. It adds fields,
tables, constraints, and indexes. It does not drop existing tables. Existing
users receive their username as the initial display name.

5. API endpoints and responsibilities
--------------------------------------
Profiles and saved writings:
- `GET /api/users/<username>` — public profile with published contribution
  count; no email; age only when the owner made it public.
- `GET /api/users/me` and `PUT /api/users/me` — signed-in owner's private
  profile and editable profile fields.
- `POST /api/users/me/avatar` — authenticated image upload, max 3 MB.
- `GET /api/users/avatars/<filename>` — serve an uploaded profile image.
- `GET /api/users/me/saved` and `/api/users/me/saved/ids` — owner's saved list
  and IDs.
- `POST` or `DELETE /api/users/me/saved/<post_id>` — save or unsave a published
  writing for the current user.

Search:
- `GET /api/search?q=<term>&type=writings` — title/content search over
  published posts only, returning excerpts.
- `GET /api/search?q=<term>&type=users` — username/display-name search with
  public profile fields only.

Conversations:
- `GET /api/conversations` — conversations for the current participant,
  including each one's unread count.
- `POST /api/conversations/direct` with `user_id` — find or create a direct
  conversation.
- `POST /api/conversations/groups` with `name` and `member_ids` — create a
  named group; creator becomes its administrator.
- `GET /api/conversations/<id>` — conversation and participants, membership
  required.
- `GET /api/conversations/<id>/messages` — persisted history, membership
  required; `limit` and `before` support older-page retrieval.
- `POST /api/conversations/<id>/messages` with `body` — validate and persist a
  message, then emit it to joined conversation sockets.
- `POST /api/conversations/<id>/read` — update the caller's read timestamp.
- `POST /api/conversations/<id>/participants` — administrator adds users.
- `DELETE /api/conversations/<id>/participants/<user_id>` — administrator
  removes a member.
- `POST /api/conversations/<id>/leave` — a group member leaves; sole admin
  rights transfer to another member when needed.

Post engagement and media:
- `POST /api/posts/<id>/like` — toggle a like for the signed-in user.
- `GET /api/posts/<id>/comments` and `POST /api/posts/<id>/comments` — read
  and add comments to published posts.
- `POST /api/posts/<id>/media` and `DELETE /api/posts/<id>/media/<media_id>` —
  add or remove up to five image, audio, or video attachments.
- `GET /api/posts/media/<filename>` — serve attachments; draft media remains
  private to its author.

Every conversation and message route returns 404 for a non-member, avoiding
information leaks about private conversation IDs. Group participant changes
require administrator membership. Socket events are `join_conversation`,
`send_message`, and `new_message`.

6. Real-time messaging concepts
-------------------------------
REST remains the source for conversation lists and message history. Socket.IO
keeps a connected page informed without polling. A room is a server-side group
of sockets for one conversation; only validated members join it. JWT
authentication identifies a socket user. Membership is checked both when
joining and when sending. The server persists each message before broadcasting
it, so the database remains the record after refresh or reconnect.

7. Search implementation
------------------------
The search form waits 350 ms after the last keystroke and then calls the
selected backend search type. An AbortController cancels obsolete requests.
SQLAlchemy searches the database with case-insensitive matching. `%` and `_`
are escaped so they behave as literal input. Writing search explicitly filters
to `published`; draft content and private account fields are not returned.

8. Profile and privacy implementation
-------------------------------------
The public profile serializer returns username, display name, avatar, bio, and
published contribution count. It never calls the private user serializer and
does not include email. It adds age only after checking `age_public`. Private
account data is read and edited through token-protected `/me` endpoints.
Contributions use a database count of posts whose status is published. Avatar
uploads accept PNG, JPEG, and WebP, validate the file signature and size, save
with a generated filename, and store only the served URL on the user.

and a non-default `SECRET_KEY`. Install the server dependencies, then run:

    cd server
    python -m pip install -r requirements.txt
    python -m flask --app run db upgrade
    python -m pytest -q
    python run.py

age privacy and contribution counts, avatar validation/serving, database
search without drafts, local registration, draft creation/edit/publication,

12. Common errors and debugging
-------------------------------
- `DATABASE_URL` missing or refused: start PostgreSQL and set the URL in
  `server/.env` before running Flask or migrations.
- New columns/tables missing: run `python -m flask --app run db upgrade` from
  the server folder and confirm the current head is `8d4c2b91f6a0`.
- Socket shows disconnected: keep Flask on port 5000 and Vite on 5173, and
  confirm the page origin is allowed by `SOCKETIO_CORS_ALLOWED_ORIGINS` and the
  connection reaches Flask. Production proxies need WebSocket upgrade support.
- Socket says authentication required: sign in again so the current JWT is
  present in `midnight_token`; expired tokens are rejected.
- A conversation returns 404: confirm the signed-in user is a participant.
- Avatar upload fails: use PNG, JPEG, or WebP no larger than 3 MB; ensure the
  configured avatar folder is writable and persistent.
- Search looks empty: verify that the writing is published, not a draft, and
  search text matches a title/content or username/display name.
- Creator image is missing in a build: preserve the existing
  `assets/images/creator.png` file at the repository root.

13. SDE interview questions and answers
---------------------------------------
1. Why use a migration instead of recreating tables?
   A migration changes the schema in small steps while keeping existing rows.
   This migration adds columns and new tables, then fills the initial display
   name from the old username.

2. How does the API keep profile email private?
   Public routes use `to_public_dict`, which has an explicit allowlist of
   public fields. The private `to_dict` serializer is used only on authenticated
   owner routes and auth responses.

3. How is age privacy enforced?
   The public serializer checks `age_public` on the server before adding age to
   its response. Hiding a field only in React would not protect the API.

4. How is the contribution count made meaningful?
   The service counts database posts with the user's ID and published status.
   It does not trust a browser-supplied total or include drafts.

5. Why have a SavedWriting table?
   A separate relationship row connects a user and a post and records when it
   was saved. A unique constraint prevents duplicate bookmarks and foreign
   keys clean up rows when their user or post is removed.

6. How are direct conversations kept unique?
   The two participant IDs are sorted and joined into a stable direct key. A
   database unique constraint prevents two requests from creating duplicates.

7. How does the server stop a user reading another conversation?
   Every REST history/detail request verifies a participant row. The socket
   server also checks membership before joining a room and before saving a
   socket message.

8. Why persist before broadcasting a message?
   The database remains the source of truth. If a browser disconnects during
   delivery, the recipient can still load the saved message from history.

9. What is a Socket.IO room?
   It is a server-managed group of connected clients. This app names a room for
   each conversation and only joins a socket after checking membership.

10. What is the JWT used for on a socket?
    The client sends its existing application token during the connection
    handshake. Flask verifies it and records the user ID for later membership
    checks, just like the REST authorization flow.

11. Why debounce search?
    A short delay waits until typing pauses, reducing duplicate database
    requests. AbortController cancels a stale request when the query or tab
    changes.

12. Why filter drafts on the backend?
    A frontend filter can be bypassed. The writing query itself requires
    published status, so a draft is never included in a public search response.

13. Why validate avatar signatures as well as MIME type?
    A browser-provided content type can be false. A size limit and file
    signature check reduce accidental or disguised non-image uploads.

14. What is the role of a conversation participant record?
    It both grants access and stores the member's role, join time, and last-read
    time. It is the common authorization check for REST and sockets.

15. Why test using two socket clients?
    One client sending to itself cannot prove delivery to another user. The
    integration test authenticates separate clients, joins the same room, sends
    a message, and verifies the recipient receives the event.

16. Key takeaways
-----------------
Keep public serializers deliberately small, enforce membership at every data
boundary, and store messages before sending live events. Search and contribution
counts should come from database queries. Migrations should extend a working
schema rather than replacing it. A later additive migration adds persisted post
likes, comments, and media attachments. The About page includes the creator
details supplied by the project owner.
